# 장터 수수료 일정 (fee schedule) — 서명된 목록의 「블록 높이별 요율」

작성 2026-10-11. 대표 확정: 장터 수수료를 **서명된 목록 묶음의 요율 일정**으로 운영하고 코드의 15% 초안 상수를 없앤다.
같은 문서가 두 저장소에 있다: 지갑 `ravenvault` 브랜치 `claude/rv-signed-lists-core`(기준 `02ba506`), 데스크탑 `playx-raven` 브랜치 `claude/rv-signed-lists-desktop`(기준 `09d23b6`).

**하지 않은 것**: 운영 키 생성, 실제 일정 서명·배포, push·배포·태그, 메인넷 거래·송금. 시험은 전부 일회용 키·모의 체인. 수수료 주소 시험은 일회용(개인키 없는) 주소.
**출하 상태**: 목록 키·일정 키가 비어 있어 출하 지갑·데스크탑은 일정을 받지 않는다 → 「일정 없음」 → 구매 거래를 만들지 않는다(`MISSING_SCHEDULE_POLICY = 'refuse'`). 판매 스위치(`OPEN_MARKET_SALES_ENABLED`)도 꺼진 채.

## 2. 데이터 형식 `rv-fee-schedule` v1

```json
{ "format": "rv-fee-schedule", "version": 1, "scheduleId": "rv-market",
  "launch": { "height": 4000000, "timeNote": "2026-12-01T00:00:00Z" },
  "rules": { "*":      { "freeBlocks": 263520, "bps": 500, "founders": true, "volume": true, "capAtoms": "50000000000", "freePrice": true },
             "ticket": { "freeBlocks": 0,      "bps": 500, "founders": true, "volume": true, "capAtoms": "50000000000", "freePrice": true } },
  "founders": { "bps": 250, "blocks": 525600, "sellers": ["R…"] },
  "volume":   { "bps": 300, "thresholdAtoms": "100000000000000", "sellers": [{ "address": "R…", "year": 2027, "fromHeight": 4300000, "untilHeight": 4700000 }] },
  "regions":  { "mode": "none" } }
```

- 모르는 칸·빠진 칸 거절. `rules` 는 `'*'` 필수 + 종류(`game·music·book·ticket·digital`)별 덮어쓰기.
- **안쪽 서명**: 자기 도메인 `RAVENVAULT-FEE-SCHEDULE-V1`, 서명 형식 `rv-fee-schedule-signature`(허용 목록과 같은 Ed25519 분리 서명 모양, 도메인만 다름 — 다른 목록 서명을 재사용할 수 없다, 시험).
  믿는 키 = `FEE_SCHEDULE_PUBLIC_KEYS`(비어 있음) + 믿는 목록 키(키 전환 반영).
- **바깥 묶음**: 기존 `rv-signed-lists` v1 의 네 번째 칸 `feeSchedule`. 일련번호·만료·되돌림 거절·부분 적용 금지·키 전환은 기존 규칙 그대로.
  `feeSchedule` 칸이 없는 옛 세 칸 묶음도 받는다(일정 없음). 서명기는 늘 네 칸을 쓴다.
- 매니페스트(상품)는 요율이 아니라 **일정 참조**를 담는다: `fee: { policy: "rv-fee-schedule-v1", scheduleId: "rv-market" }`.

## 3. 판정 규칙 — 기간은 **체인 블록 높이**로 (로컬 시계 불신)

- 시작·무료 끝·창립 끝·누적 구간은 전부 블록 높이다. `launch.timeNote` 는 화면의 「예상 날짜」에만 쓰고 판정에 쓰지 않는다.
- **구매(지갑이 거래를 만들 때)**: 요율 = 두 독립 출처가 합의한 체인 팁 높이 + 1(다음 블록)의 요율(`checkCreatorPurchase({ tipHeight })`). 팁이 없으면 팔지 않는다(`chain-unavailable`).
  기기 시계가 2030년이어도 체인이 무료 기간이면 0%(시험).
- **기록된 구매 판정(검증기)**: 포함 블록 높이 H. 정당한 요율 = **[H − 120, H] 안에서 한 번이라도 유효했던 요율 중 하나와 정확히 맞으면** 정당(`verifyCreatorPayment`, `acceptableRates`).
  - 이유: 견적은 팁 + 1 에서 하지만 거래가 늦게 채굴될 수 있다. 120 블록(약 2시간) = 견적 15분 + 멤풀 지연 여유.
  - 「낮은 쪽까지」가 아니라 「그 창 안의 요율 중 하나」인 이유: 판매자 출력은 「가격 − 그 요율의 수수료」 이상이어야 해서, 0% 거래(판매자 300)와 5% 거래(판매자 285 + 수수료 15)는 서로 다른 모양이다. 둘 중 하나와 맞으면 된다.
  - 경계 블록 자체는 새 요율이다(`height >= freeEnd` → 5%).
  - 블록 **시각**을 쓰지 않으므로 채굴자의 시각 조작(±2시간)이 판정에 영향이 없다. 직접 결제의 「블록 시각 기준 RVN 가격표」와 같은 생각(포함 블록으로 판정, 견적 값을 믿지 않음)이되 기준을 높이로 바꿨다.
- **게임 원본 검증기(direct-verify.js)와의 일치**: 지갑이 포함 높이의 요율 하나로 등록부 항목(`creatorGameEntry(listing, bps)`)을 만들어 넘기면 게임 검증기는 출력 규칙(판매자 ≥, 수수료 ≥, 정확히 1개)을 그대로 적용한다. 0%·5%·누락·다른 주소·부족·경계 전 5% 6가지에서 지갑 판정과 같은 결과(시험).

## 4. 누적 구간(연 100만 RVN)·창립 판매자 — 서버 없이 할 수 있는 만큼

- 판매자별 연 누적은 서버(색인기) 없이 지갑이 알 수 없다: 판매자 받는 주소는 상품마다 다를 수 있고, 모든 지갑이 모든 판매 기록을 훑을 수 없다.
- 그래서 **근사가 아니라 선언**으로 바꿨다: 대표가 체인 기록(메모가 있는 구매 거래)을 세어 「그 해 100만 RVN 을 넘은 판매자」를 `volume.sellers[]` 에 `{주소, 해, fromHeight, untilHeight}` 로 올린다.
  `untilHeight` = 다음 해 1월 1일 0시(KST)의 블록 높이 어림 → 해마다 초기화.
- **한계**: 목록에 오르기 전까지의 초과분은 5% 그대로다(넘은 순간의 그 판매를 둘로 쪼갤 수도 없다). 선언이 늦을수록 판매자가 더 낸다 → 대표가 필요하면 차액을 수동 정산(결정 #4).
- 창립 판매자도 주소로 명시(제작자 주소 또는 받는 주소 어느 쪽이 같아도 적용). 최대 50명은 코드 천장.
- 둘 다 해당하면 낮은 쪽(2.5%).

## 5. 상품당 상한 500 RVN · 올림 규칙

- `fee = ceil(price × bps / 10000)`(정수 atoms, 플랫폼 쪽 올림), `seller = price − fee`, 먼지 하한 1000 atoms — 기존 `splitPrice`(게임 `platform-fee.js` 와 무작위 대조) 그대로.
- 상한은 「수수료 ≤ 500 RVN 인 **가장 큰 정수 bps**」로 요율을 낮춰 구현(`capBps`). 그래서 거래·게임 검증기·등록부 항목이 여전히 bps 하나로 표현된다.
  예: 10,000 RVN × 5% = 정확히 500(상한 아님), 10,001 RVN → 499 bps(수수료 499.05 RVN), 20,000 RVN → 250 bps(500 RVN).
  실제 수수료는 상한 이하이고 차이는 가격의 0.01% 미만(판매자 쪽 유리). 1 bps 로도 넘는 가격(5,000,000 RVN 초과)은 팔지 않는다(`cap-range`).

## 6. 요율 0 기간의 거래 — 「0 출력」 대신 메모 + 일정

- 레이븐코인(비트코인 계열)은 0 RVN 일반(P2PKH) 출력을 **먼지 = 비표준**으로 보아 노드가 중계하지 않는다(확신: 중간 — 비트코인 정책 코드의 `IsDust`/`IsStandardTx` 를 이어받았다는 기억에 기댐, 레이븐코인 원본 대조 안 함).
  그래서 「수수료 0 출력」은 만들지 않는다.
- 대신: **RVDP v3 메모(OP_RETURN, 0 RVN 허용)가 늘 있다** → 판매 기록·영수증(어느 상품·누가·언제)은 체인에 남는다. 「요율 0 이 정당한가」는 검증기가 그 블록 높이의 서명된 일정으로 다시 계산해 확인한다(메모에 요율 칸을 새로 넣지 않음 — 메모 형식 v3 를 바꾸면 게임 검증기와 어긋난다).
- 지갑 서명 직후 재검사(`inspectDirectPayment`)는 수수료 0 이면 수수료 출력 0개를 요구한다(기존 규칙). 거래 = 판매자 + 메모 + 잔돈(시험).
- 판매자 주소 = 수수료 주소는 0% 기간에도 거절(우회 모양).

## 7. 이행 규칙(옛 매니페스트·옛 묶음·요율 변경)

| 경우 | 규칙 |
|---|---|
| 새 매니페스트 | `{policy:'rv-fee-schedule-v1', scheduleId}`. 가격은 천장 5% 로 나눠도 판매자 몫이 남아야 한다 |
| 옛 매니페스트 `{policy:'rv-platform-fee-v4', declaredBps}` | 선언 = 「제작자가 동의한 최대 요율」. 선언 ≥ 5%(검증됨이면 min(허용 목록 feeBps, 5%)) 이면 `rv-market` 일정을 따른다, 아니면 결제 없음(`fee-mismatch`). 메인넷 발행 스위치가 꺼져 있어 실제로 나간 옛 상품은 없다 |
| 허용 목록 `feeBps`(검증됨) | 등식 검사 → **그 상품의 최대 요율**로 의미 변경. 일정 요율보다 낮으면 그 값(예: 0 = 회사 자기 상품). 형식(0~1500)은 그대로라 기존 서명 목록이 유효 |
| 요율 변경 | 새 일정(일련번호 + 1)을 서명해 올리면 끝. 상품은 일정 참조라 계속 팔린다(시험: 5% → 4% 일정 교체 뒤 같은 상품 구매) |
| 일정 칸 없는 옛 세 칸 묶음 | 받는다(일정 없음) |
| 받은 일정이 만료 | **마지막으로 검증된 일정 유지**(요율은 신뢰 부여가 아니라 정책 — 차단 목록과 같은 처리). 허용 목록은 기존대로 기본값 |
| 일정을 한 번도 못 받음 | `MISSING_SCHEDULE_POLICY = 'refuse'`: 구매 거래를 만들지 않는다. `'base-rate'`(처음부터 5% 고정 일정)는 한 줄로 바꿀 수 있다(결정 #2) |
| 일정 시작 전 높이 | 구매 닫힘(`before-launch`) |

## 8. 운영 절차 (대표)

1. 초안: `node --import tsx scripts/signed-lists/fee-schedule-draft.ts --launch-height <시작 블록> --launch-time <ISO> [--founders f.json] [--volume v.json] [--regions r.json] --out fee-schedule.json` (키 없음).
2. 후보 파일(`review-queue.ts candidate` 결과)의 `parts.feeSchedule` 에 `{ "doc": <fee-schedule.json>, "listVersion": <이전 + 1> }` 을 넣는다(review-queue 는 기존 일정을 서명째 이어 싣는다).
3. 서명: `sign-lists.ts sign --input candidate.json --key-file <대표키> --out signed-lists.json` → 스스로 다시 검증해 통과해야 파일을 쓴다.
4. 올리기: 기존 `release-site/lists/signed-lists.json`(또는 IPFS 포인터).
5. 해마다 1월 초: 지난해 판매 기록으로 `volume.sellers` 갱신. 창립 판매자 확정 시 `founders.sellers`. 30일 만료 전 재서명(만료돼도 일정은 유지되지만 허용 목록이 기본값으로 돌아간다).

## 9. 화면 (자동)

- 마법사 안내·③ 가격·⑤ 비용·⑦ 확인, 장터 구매 확인이 전부 `feeNotice`/`marketRate` 로 일정에서 숫자를 읽는다(15% 하드코딩 없음 — 시험이 문자열로 확인).
- 일정이 있으면: 「지금 수수료 0% (무료 기간) → 2027년 4월 2일 무렵(블록 4262520)부터 5%」 + 300 RVN 예시를 두 요율로 + 내 가격 계산 + 규칙 한 줄 + 「기간은 체인 블록 높이로」.
  데스크탑은 메인넷 노드가 다 따라잡았을 때만 그 높이를 쓰고, 아니면 시작 시각으로 어림해 「무렵(예상)」이라고 적는다.
- 일정이 없으면(출하 상태): 「수수료 일정을 아직 받지 못했어요 → 판매는 서명된 수수료 일정을 받은 뒤 열려요」 + 정책 출발값으로 만든 예시(무료 기간 0 / 그 뒤 285·15) + 규칙 한 줄. 장터 구매 확인은 잠긴다.
- 티켓을 고르면 「티켓은 무료 기간 없이 처음부터 5%」. 티켓 책임 문구(환불·행사 취소·재판매 책임은 제작자, 법률 확인 필요)는 그대로.

## 10. 위험

- **블록 수 ≠ 달력**: 「6개월」「12개월」「1월 1일」은 1분 = 1블록 환산이다. 실제 블록 간격이 다르면 며칠 어긋난다. 약속을 날짜로 했다면 일정 작성 때 높이를 실측으로 다시 잡아야 한다(시작 뒤에 `launch.height` 를 바꾸면 무료 기간이 바뀐다 — 신중히).
- **종류별로 요율이 다르면 종류 거짓 선택 위험**: 티켓은 시작부터 5%, 게임·음악은 무료 기간 0% → 티켓을 「디지털」(X)로 올려 수수료를 피할 수 있다. 이름의 종류 글자·매니페스트 type·파일 검사가 일부 막지만(티켓은 파일 없이도 되고 디지털은 그림·PDF 를 받는다) 내용으로 「이건 티켓」을 판별하지 못한다 → 신고·차단 목록으로 사후 대응.
- 목록 키 = 요율을 0~5% 사이에서 원격으로 바꿀 권한. 주소는 못 바꾼다.
- 누적 구간은 선언이 늦은 만큼 판매자가 더 낸다(§4). 창립 판매자 선정 기준은 대표 결정.
- 0 출력 비표준 판단은 원본 미대조(§6). 틀렸다 해도 「출력을 안 만든다」 쪽이라 안전하다.
- 경계 허용 120 블록 안에서는 두 요율 모두 정당 → 그 창 안에서 판매자가 일부러 0% 거래를 늦게 채굴시키는 이득은 최대 2시간·경계 한 번.
- 지갑이 받은 팁 높이가 오래된 것(두 출처가 함께 뒤처짐)이면 견적 요율이 틀릴 수 있다 → 검증기가 포함 높이로 다시 판정해 늦은 거래는 거절된다(구매자 손해 가능, 기존 직접 결제의 가격 변경 창과 같은 성격).
- 게임 저장소 쪽 검증기는 「장터 일정」을 모른다. 장터 구매를 게임 서버가 독자 검증하려면 지갑이 만든 높이별 항목을 넘겨받거나, 게임 저장소에 같은 일정 판정을 넣어야 한다(후속).
- 법률·세무(수수료 성격·고지·지역 제한)는 전문가 확인 필요.
