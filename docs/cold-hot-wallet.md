# 한 지갑 안의 금고와 용돈 지갑

설계 초안 · 2026-10-06 · 4쪽 구성. 이번 구현은 모의 서명 전용이며 실제 키 저장·인증·체인 송신을 연결하지 않는다. 아래 제품 정책과 출시 전 조건을 현재 구현과 구분한다.

## 1쪽 — 사용 경험과 위협 모델

사용자는 지갑 하나를 연다. 그 안에 **용돈 지갑(핫)**과 **금고(콜드)**를 나란히 보여 준다. 총액은 요약일 뿐, 즉시 결제 가능한 금액은 용돈 잔액과 남은 한도 중 작은 값이다. 들어오는 중인 돈은 확정 잔액에 섞지 않는다. 계정 추가·지갑 전환·시드 선택을 일상 결제에 요구하지 않는다.

용돈은 사용자가 정한 소액만 보유한다. 라비 에이전트·게임·간식 결제에는 핫 전용 권한만 준다. 수수료 포함 1회·하루 한도 안이면 즉시 처리한다. 최초에 자동 결제 범위에 동의하고 결제 후 내역과 알림을 제공한다. 한도를 넘으면 실행을 멈추고 금고 승인 화면으로 안내한다. 금고 승인으로 핫 한도를 잠깐 해제하거나 여러 결제로 쪼개지 않는다. 큰 송금은 별도의 금고 거래로 다시 검토한다.

금고는 평소 잔액·주소만 보는 감시 전용이다. 금고→핫 이동과 큰 송금만 소유자의 매 거래 인증 후 서명한다. 핫이 모자라면 라비는 “금고에서 얼마 옮길까요?”라고 묻는다. 답변은 제안일 뿐 승인 증명이 아니다. 금액 선택·주소·수수료 확인·비밀번호 또는 생체 인증을 소유자 화면에서 마쳐야 한다. 잔액 임계값·예약 작업·AI 판단으로 자동 이체하지 않는다.

| 위협 | 방어와 신뢰 경계 | 남는 위험 |
|---|---|---|
| 프롬프트 주입·악성 게임 | 핫 capability만 주입, 명령 허용목록, 금고 모듈의 전이적 import 금지 시험 | 허용된 핫 한도까지 오용 가능. 가맹점 검증·사용자 알림은 별도 필요 |
| 더블클릭·동시 호출·분할 결제 | 서명 전에 금액+수수료 예약, 전체 핫 호출의 일일 누계 공유 | 다중 기기에서는 원자적 공용 원장이 필요 |
| 승인 재사용·승인 뒤 주소 바꾸기 | 불변 거래에 인증 결속, 120초 만료, 일회성 상태 전이 | 실제 서명기는 입력·출력·거스름돈까지 거래 전체를 재검증해야 함 |
| 분실·파일 탈취 | 시드 분리, 금고의 암호화 저장 또는 외부 서명 | 약한 암호·백업 유출·복구 수단 분실은 해결하지 못함 |
| OS/렌더러 장악·시계 조작 | 외부 서명 장치, 별도 인증 경계, 시간 역행 거부 | 같은 프로세스의 TypeScript는 악성코드에 대한 격리 장치가 아님 |

신뢰 대상은 소유자 인증 UI, 정책 집행 서비스, 잔액·수수료 관측기와 서명기다. AI 응답·게임 인자·브라우저 저장값·원격 RPC의 오류 원문은 신뢰하지 않는다. 로그에는 결과 코드와 집계만 남기며 시드·토큰·비밀번호·서명 원문은 기록하지 않는다. 이번 시험은 네트워크가 없는 모의 객체만 쓴다.

## 2쪽 — 키 구조와 보관 선택

**금고 시드와 용돈 시드는 독립된 난수로 각각 만든다.** 하나의 마스터 시드에서 계정 번호만 나누는 설계는 채택하지 않는다. 핫 시드가 유출돼도 금고 시드를 유도할 수 없어야 한다. 일상 화면에 시드를 보여 주는 기능은 없으며 이 모듈에는 시드·개인키·비밀번호 필드 자체가 없다.

각 시드에서 BIP32 HD 트리를 만들고 BIP44 형태 `m/44'/coin_type'/account'/change/index`로 주소를 파생하는 방안을 사용한다. 앞 세 단계는 hardened, 수신은 change=0, 거스름돈은 change=1이다. 독립 시드 각각의 account=0부터 시작한다. 테스트넷 제안 경로는 `m/44'/1'/0'/0/i`, 거스름돈은 `…/1/i`다. 실제 연결 전 선택한 Ravencoin 서명기의 테스트넷 파생 규칙을 검증한다. 경로 숫자는 키 분리의 근거가 아니며 **독립 시드가 분리의 근거**다. [BIP32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki), [BIP44](https://github.com/bitcoin/bips/blob/master/bip-0044.mediawiki), [SLIP-0044](https://github.com/satoshilabs/slips/blob/master/slip-0044.md)

기존 웹 지갑의 RVN 경로 `m/44'/175'/0'/0/i`는 이 설계와 자동 병합하지 않는다. 이번 코드는 파생·키 생성도 하지 않는다. 향후 마이그레이션은 기존 지갑을 그대로 인식한 뒤 새 핫 지갑으로 옮길 금액을 사용자가 승인하는 별도 작업이다. 입력 UTXO·거스름돈도 지갑별로 분리해 핫 거래에 금고 입력을 끼워 넣지 않는다.

| 선택 | 앱이 평소 가지는 정보 | 서명 순간 |
|---|---|---|
| (a) 앱 내 암호화 보관 | 금고 주소·잔액, OS 보호 저장소의 암호문 참조 | OS 인증/비밀번호 확인 후 별도 서명 서비스에서 잠깐 복호화, 거래별 서명 후 즉시 잠금 |
| (b) 하드웨어/오프라인 | 사용자가 등록한 감시 전용 주소와 네트워크만 | 거래 검토·로컬 인증 후 외부 기기에서 주소·금액 확인 및 서명, 돌아온 결과 검증 |

(a)는 엄밀한 오프라인 콜드월렛이 아니다. 명칭 옆에 “이 기기에 암호화 보관”을 항상 표시한다. 구현 시 검증된 암호 라이브러리의 인증 암호화, 적절한 암호 KDF, 매 암호문 난수 salt/nonce, OS 보호 저장소를 사용하고 키를 localStorage에 두지 않는다. 비밀의 수명은 최소화하되 JS 메모리 완전 삭제를 약속하지 않는다. 구체 암호 포맷은 별도 보안 검토 대상이다.

(b)는 금고 시드를 앱에 넣지 않는다. 주소만 등록하면 신규 주소·거스름돈의 자동 탐색은 제한된다. 추가 주소는 외부 기기에서 확인해 등록한다. 향후 확장 공개키를 지원한다면 계정 범위만 허용하고 주소 연결성 노출을 설명한다. 하드웨어가 RVN/테스트넷을 지원한다고 가정하지 않으며, 확인된 기기·경로만 지원 목록에 올린다.

복구는 사용자가 한 지갑으로 이해하더라도 내부적으로 두 독립 자산이다. 별도 보호 백업과 외부 기기의 복구 절차가 필요하다. 역할·네트워크·파생 경로·주소 인덱스 메타데이터를 함께 보존한다. 금고 시드를 화면에 출력하지 않는 요구와 실제 복구 절차를 양립시키는 안전한 백업·복구 UX가 검증되기 전에는 키 생성 기능을 출시하지 않는다.

## 3쪽 — 한도 정책, 상태 기계, 화면 흐름

원자 단위 `bigint`로 계산한다. `총 출금 = 수신 금액 + 수수료`이며 부동소수점·음수·0원 송금은 거부한다. 한도는 `0 ≤ 1회 ≤ 하루`, 같은 사용자의 라비·게임·간식 결제를 모두 합산한다. 자산 토큰·환율 기반 한도는 범위 밖이며 RVN 원자 단위 한 종류만 가정한다. 실제 거래 크기와 자산 검증은 향후 서명 어댑터의 책임이다.

| 상황 | 처리 |
|---|---|
| 총 출금 ≤ 1회, 당일 예약 합계+총 출금 ≤ 하루, 잔액 충분 | await 전에 한도·잔액 예약 → 핫 서명 |
| 1회/하루 한도 초과 | `needs_vault_approval`; 금고 자동 호출 없음 |
| 한도 안이지만 핫 잔액 부족 | `needs_topup`; 질문만, 금액은 사용자가 선택 |
| 실패 또는 결과 불명 | 예약 유지. 원문 오류 대신 코드 표시, 자동 재시도 금지 |

자정은 사용자에게 표시한 **고정 UTC 오프셋** 기준이다(기본 제안 UTC+09:00). OS 시간대 변경으로 정책을 바꾸지 않는다. 다음 날 첫 조회/요청 때 누계를 0으로 만들고, 예약으로 줄어든 잔액은 복원하지 않는다. 집계 날짜는 서명 완료가 아닌 **예약 시각**이다. 자정을 넘긴 미완료 서명은 전날 예약에 속한다. DST 지역은 고정 오프셋임을 표시한다. 시간 역행은 거부하지만 조작된 미래 시각은 현 모듈만으로 탐지할 수 없다. 실제 서비스는 신뢰 시각과 영속 원장의 마지막 날짜를 확인해야 한다.

한도·시간대는 세션 중 변경 불가다. 향후 한도 증가·시간대 변경은 소유자 재인증과 정책 버전 갱신을 요구하고 당일 지출을 보존한다. 초기 한도를 임의로 크게 정하지 않고 최초 설정에서 사용자가 금액을 선택한다. 백그라운드 무제한 잠금 해제나 영구 승인은 없다.

```text
금고: review → authenticating → signing → signed
         └취소/만료    ├거부/오류 → failed
                      └취소/만료 → cancelled/expired
핫: 판단 → 거부/보충 제안 또는 즉시 예약 → 모의 서명 결과
```

소유자가 거래를 준비하면 120초 유효기간의 불변 요청이 만들어진다. 인증은 그 요청의 네트워크·출처·목적·수신처·금액·수수료에 결속된다. 인증 대기 중 취소·만료되면 서명하지 않는다. 첫 await 전에 인증 중 상태로 전이하므로 더블클릭은 거부한다. 모든 종료 상태에서 재승인은 불가능하다. 내용 수정·재시도는 새 요청과 새 인증을 요구한다.

화면 흐름은 `내 지갑 → 용돈으로 보내기 → 한도 안 결과` 또는 `부족/초과 안내 → 소유자 금고 검토 → 인증 → 서명 결과 → 입금 확인`이다. 금고→핫 서명 완료를 입금 완료로 표시하지 않는다. 합산 잔액은 이체 중 중복 계산하지 않고, 전체·용돈·금고·이동 중을 구분한다. 전체 화면 텍스트 와이어프레임은 [별도 초안](cold-hot-wallet-wireframe.md), 문구는 [ko/en/ja/zh 키 사전](cold-hot-wallet-copy.json)에 둔다.

## 4쪽 — 코드 경계, 한계와 출시 조건

`core/wallet-hot.ts`는 핫 잔액/한도 조회와 결제 타입만 공개한다. `core/wallet-vault.ts`는 시간·저장소를 직접 읽지 않는 순수 한도 계산·승인 상태 전이 로직이다. `src/wallet-vault.ts`는 정책과 서명기를 조립해 `{ hot, owner }` 두 객체를 반환한다. **소유자 조립 계층만 owner를 보관**하고 AI·게임에는 hot만 전달한다. caller가 보낸 `actor: owner`, `approved: true` 같은 필드는 권한 근거가 아니며 결제 입력에서 거부한다.

`src/ravi-wallet.ts`는 `HotWalletPort` 타입만 받는다. 명령 허용목록은 `hot_status`, `hot_pay` 두 개다. 미등록 명령·여분 인자·프로토타입 이름도 런타임에서 거부한다. AI 경계의 금액은 원자 단위 정수 문자열이며 내부에서 BigInt로 바꾼다. 현 반환값의 BigInt는 향후 IPC 어댑터에서 정수 문자열로 직렬화해야 한다. 기존 라비 도구/게임 bridge와 main.ts에 결제 기능을 연결하지 않았으므로 지금 자동 결제가 추가되지는 않는다.

시험은 모든 `src/ravi-*.ts`의 정적 import·재수출·정적 경로의 동적 import를 전이적으로 따라 금고 모듈 유입을 막는다. 금고 API를 호출하는 타입 오류, AI 이름 위조의 런타임 거부, import 우회 변이 시험을 함께 수행한다. 이 경계는 **새 모듈의 capability 구조**에 대한 검증이다. 기존 범용 Tauri invoke와 기존 단일 지갑 RPC를 금고 저장소에 연결해서는 안 된다. 향후 실제 연결은 별도 네이티브 서비스·IPC 호출자 권한 검사로 경계를 재구현하고, 기존 잔액/거래 요약의 라비 전달도 핫 범위로 제한해야 한다.

모의 구현의 `VaultSigner`/`HotSigner`는 `mode: mock`만 받으며 출력은 거래 ID에 결속된 `mock-signature` 표식이다. 네트워크는 mock/testnet만 허용하고 mainnet은 거부한다. 개인키·실제 서명 바이트·방송 API는 없다. 실제 OS 인증은 주입 인터페이스만 있고 시험에서 참/거짓으로 대체한다. `signed`는 모의 서명 성공이지 체인 전송 성공이 아니다. 이 프로토타입에서 서명 완료 후 핫 입금을 확정하는 API는 제공하지 않는다.

화면에 숨기지 않고 표시할 핵심 문구:

> 같은 기기에 시드가 있으면 완전히 못 열게 할 수는 없어요. 기기가 악성코드에 감염되면 금고도 위험할 수 있어요.
